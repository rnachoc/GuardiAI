# 5. The OpenTelemetry agent and one Collector

- **Status:** Accepted
- **Date:** 2026-11-01
- **Author:** Ignacio Rodriguez Caro

## Context

Guardia investigates incidents from metrics, logs and traces, so Mercadillo must produce all three, with a trace ID that ties a log line to its request across services, Kafka included. Hand-written instrumentation in seven services would be uneven and would miss libraries such as JDBC, Redis and Kafka. The stores must also be ones that a read-only tool server can query later.

## Decision

- Each service runs with the **OpenTelemetry Java agent 2.33.1**, pinned in the Maven build and copied into every image. It instruments HTTP servers and clients, JDBC, Hikari, Redis, Kafka and Logback with no code, and exports traces, metrics and logs over OTLP. Two business counters, checkouts by outcome and notifications, use the OpenTelemetry API, which the agent provides at run time.
- One **OpenTelemetry Collector** (contrib 0.163.2) receives everything and sends each signal over OTLP to its store: traces to **Tempo 2.10.10**, metrics to **Prometheus 3.15.1** through its native OTLP receiver, and logs to **Loki 3.7.9** through its native OTLP endpoint. No vendor-specific exporter is involved.
- Prometheus copies `service.name` and a few other resource attributes onto every series, so queries filter by service directly. Tempo's metrics generator derives a service graph and span metrics from the traces, and writes them to Prometheus.
- **Grafana 13.2.5** is provisioned with linked data sources (a trace links to its logs, and a log line to its trace) and an overview dashboard. The dashboard is generated by `scripts/build_dashboard.py`, and a test fails if the committed JSON drifts from it.
- `make verify` proves the pipeline end to end on the running stack: live traffic in Prometheus, a checkout trace across at least four services in Tempo, logs from every service with trace IDs in Loki, and every Prometheus query of the dashboard returning data through Grafana.

## Consequences

- Every service is observed the same way, including libraries nobody wrote instrumentation for.
- The agent adds a few seconds to start-up and some memory to each JVM, which is why services get 768 MB.
- Metric names follow the OpenTelemetry semantic conventions as translated by Prometheus, for example `http_server_request_duration_seconds`. A change in the agent's conventions would change queries, so the agent is updated deliberately.
- The Collector, Tempo and Loki images have no shell, so Compose cannot health-check them. Services wait for the Collector to start, their exporters retry, and `make verify` checks each store's readiness endpoint.
- Container health checks also produce traces, at a slower pace once a service is up. They appear as calls from `user` in the service graph.
